# ISSUE-017 議事録作成（Claude）をどこで動かすか

| 項目 | 内容 |
|---|---|
| 区分 | 論点 |
| 状態 | 済 |
| 起票日 | 2026/11/23 |
| 対象会議 | 全般 |
| 関連 | docs/design/議事録作成ツール設計書.md 4.4、ISSUE-001、ISSUE-002 |

## 何が起きているか・何が分からないか

文字起こし・話者分離・Word 出力はスクリプト化したが、議事録の本文を作る工程（④）は Claude Code の対話の中で手作業的に行っている。ソフトにまとめるには、この工程の動かし方を決める必要がある。

## 根拠

- 現状、④の作成ルール・書式・用語集の使い方は、会話の中の指示と Issue に散らばっている。
- ヒアリングでは話者対応表を人が作る必要がある（ISSUE-001）。

## 選択肢

| 案 | 内容 | 良い点 | 懸念 |
|---|---|---|---|
| A | Claude Code のスキルだけで行う | 追加契約なし。人と対話しながら確認できる | 毎回 Claude Code を開いて頼む必要がある |
| B | Claude API を使うプログラムにする | ボタン1つで最後まで動く | API キーと利用料が必要。話者対応表など人の判断を挟む画面を別に作る必要がある |
| C | ハイブリッド：重い処理（①②③⑤）はコード、④の作成ルールはスキルにまとめ、Claude Code で実行する。作成ルールはファイルに書き出し、後で API に移せる形にする | 今の運用のまま再現性が上がる。人の確認（話者対応表・用語の追加・Issue 起票）を対話で挟める。将来 B に移しやすい | 完全な自動化ではない |

推奨：C。理由は2つ。(1) 話者対応表の作成や【要確認】の確認など、人の判断を挟む工程が残っており、対話で進められる方が手戻りが少ない。(2) スキルに書く作成ルールは、そのまま API 用のプロンプトにも使えるので、B に移る時に無駄にならない。

※どの案でも、④では文字起こしのテキストを Anthropic に送る（音声は送らない）。

## 不明点（Aさんに確認したい）

1. 議事録作成のたびに Claude Code を開いて頼む運用で問題ないか。
2. Claude API の利用（API キー・費用）は社内で認められるか。

## ソフトへの影響

④の実装方式と、人の確認画面の要否が決まる。

## 決定内容

2026/11/23 Aさん：議事録作成スキルを作ってレビューする。
- 対応：案 C の形で `.claude/skills/minutes/`（SKILL.md＋references/writing-rules.md）を作成。補助スクリプト `src/speaker_samples.py`（話者対応表用）、`src/glossary_tool.py`（用語集の読み出し・追加候補）、`src/timing.py`（作業時間の記録）を追加。Cさん（一括受電）の録音で、このスキルに沿って作成して確かめる。Aさんのレビュー待ち。

2026/11/23 Aさん：案 C（ハイブリッド）でよい。必要なところで Claude を使う方が分かりやすい。今後、議事録作成を Claude 以外で代替できないかも試していきたい → ISSUE-020。
- 対応：議事録作成スキル `.claude/skills/minutes/` で運用開始。重い処理・機械的な処理は `src/` のスクリプト、文章を書く・判断する工程（④、⑤の判断、話者の推定）だけ Claude が行う。
