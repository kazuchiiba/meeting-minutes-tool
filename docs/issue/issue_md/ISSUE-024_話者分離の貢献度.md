# ISSUE-024 話者分離（pyannote）は議事録の精度にどこまで貢献しているか

| 項目 | 内容 |
|---|---|
| 区分 | 論点 |
| 状態 | 検討中 |
| 起票日 | 2026/11/23 |
| 対象会議 | 11/20 CI、11/20 Bさんヒアリング、11/20 Cさん（一括受電） |
| 関連 | ISSUE-001（話者分離）、ISSUE-018（高速化）、ISSUE-022（2名の会議で機能しない）、検証計画 4.3「話者誤り」 |

## 何が起きているか・何が分からないか

話者分離（②、pyannote）は処理時間の大半を占めるが、議事録の精度にどれだけ効いているかを測っていない。これまでの試行では、pyannote の誤りを Claude が内容から補っている場面と、pyannote がほぼ役に立っていない場面がある。

明らかにしたいこと：
1. pyannote を使うと、使わない場合に比べて議事録の「話者誤り」がどれだけ減るか（定量）
2. pyannote が必要な会議の種類（人数・形式）と、省略してよい会議の種類
3. 2 を踏まえて、pyannote を常に使うか、使い分けるか、やめるか

## 根拠

**処理時間（ISSUE-018）**
- Cさん（38分）：①文字起こし 28.2分、②話者分離 72.5分、③抜けの補完 8.9分（`transcripts/20261120_Cさん(一括受電)/…timing.json`）。②が①〜③の 66%。
- 話者分離だけを動かすと音声の約1.9倍かかる。そのうち約97%が「声の特徴量」の計算（`transcripts/20261120_CI/step_eval/2245+500/report.md`）。

**これまでの精度（ISSUE-001、ISSUE-022、検証計画 7章）**

| 会議 | 形式 | pyannote の結果 | 議事録の話者誤り |
|---|---|---|---|
| CI（5人） | 司会が順に指名 | 2名（Gさん・Eさん）を1人と判定 | 0件。Claude が内容から振り分けた |
| Bさんヒアリング（6人） | 自由に発言 | 6つの記号に分かれた | 13発言。原因は記号と氏名の対応付けの誤り（1か所の聞き違い）で、分離そのものの誤りではない |
| Cさん（2人） | 対話 | 会話の大半が1つの記号にまとめられた | 発言者はすべて内容から推定し【推定】を付けた |

**もう1つの役割：抜けの補完（③、ISSUE-011）**
pyannote が検出した発話区間は、Whisper が取りこぼした発話を探すのにも使っている。ISSUE-022 のセッションが作った「話者分離なし」（③を pyannote なしでやり直したもの）と比べると、次のとおり（`transcripts/<名前>/` と `transcripts/<名前>_話者分離なし/` の .srt・.json の文字数）。

| 会議 | Whisper の出力 | 補完後（pyannote あり） | 補完後（pyannote なし） |
|---|---|---|---|
| CI | 6,829字 | 7,217字（+388） | 6,867字（+38） |
| Cさん | 6,440字 | 6,679字（+239） | 6,657字（+217） |

- CI では、pyannote がないと補完で戻る文字が 1/10 になる。21:22–22:34 のDさんの報告（72秒）は、pyannote がないと1セグメントしか戻らなかった。
- Cさんでは差が小さい。
- つまり pyannote は、話者の付与とは別に「発言の取りこぼし（網羅）」にも効いている可能性がある。比較では網羅も合わせて見る。

- 話者の付与については、pyannote が明確に役立った会議はまだ確認できていない。一方で、pyannote がない場合の議事録は、まだどの会議でも作っていない。

## 評価方法（案）

同じ音声で「pyannote あり」と「pyannote なし（`run_pipeline.py --no-diarize`、ISSUE-022）」の議事録を作り、同じ基準で比べる。

**比べる条件**

| 条件 | 内容 |
|---|---|
| あり | 今の構成（pyannote 3.1、窓のずらし幅 1秒） |
| なし | Whisper の出力だけ。発言者は Claude が内容から推定する |
| （参考）軽い設定 | ずらし幅を広げた pyannote（ISSUE-018 の比較で精度の落ちが小さかった幅） |

**会議の種類**：形式ごとに pyannote の効き方が違うと見込むので、3種類で測る。

| 会議 | 形式・人数 | 正解（話者） | 見込み |
|---|---|---|---|
| CI | 指名型・5人 | 人手版 R | 指名で区切られるので、なしでも推定しやすい |
| Bさんヒアリング | 自由発言・6人 | 人手版 R | なしだと推定が難しい。pyannote が効くならここ |
| Cさん | 対話・2人 | R がない → Aさんが参加者なので、抜き出した50発言に正しい話者を付けてもらう | 質問する側・説明する側で区別しやすい |

**指標**

| 指標 | 定義 | 使い方 |
|---|---|---|
| 話者誤り率（主指標） | 議事録の発言者付きの記載のうち、正解と発言者が違う割合（検証計画 `hasSpeakerError`） | あり・なしの差を見る |
| 【推定】の割合 | 発言者に【推定】が付いた記載の割合 | 人が確認する手間の目安 |
| 話者を書けなかった記載 | 【要確認：話者】の件数 | 同上 |
| ②の処理時間 | 話者分離にかかった時間と、全体に占める割合 | 精度の差と天秤にかける |

**判定基準（案）**：会議の種類ごとに判定する。

- **pyannote が必要**：次のどちらかに当てはまる。
  - なし版の話者誤り率が、あり版より 5ポイント以上高い
  - なし版の話者誤り件数が R を超える（検証計画の合格基準4「C の話者誤りが R 以下」を満たさなくなる）
- **省略してよい**：上のどちらにも当てはまらない。【推定】の割合が増える分は、人が確認する手間として別に記録する。

**作業**

| 作業 | 所要の見込み |
|---|---|
| CI・Cさんのなし版の文字起こし | ISSUE-022 で作成済み |
| Bさんのなし版の文字起こし | 既存の文字起こしを再利用し、抜けの補完だけ。10分程度 |
| なし版の議事録3本 | Claude で各15〜30分 |
| R との話者の照合 | 3本分 |
| Cさんの正解付け | Aさんに依頼（50発言） |

## 比較結果（2026/11/23）

R の発言者付きの記載ごとに、各版の同じ記載に付いた発言者を照合した。
- 照合は、どの版がどの作り方か知らない別の Claude が行った。
- 採点表：scratchpad の `eval_nishiyama/scores.tsv`・`eval_ci/scores.tsv`。必要なら docs/verification へ移す。
- 誤り率 ＝（誤り＋【推定】付きの誤り）÷ 対応する記載がある件数。

**Bさんヒアリング（自由発言・6人、R の記載 102件）**

| 版 | pyannote | 話者と氏名の対応付け | 誤り率 | 【推定】なしで正解 | Fさん以外の誤り率 |
|---|---|---|---|---|---|
| 話者記号なし | なし | Claude が内容から推定 | **21.2%**（21/99） | 59% | **10.0%** |
| 基本試行 | あり | AI が推定（Fさん→Dさんと誤認） | **20.3%**（15/74） | 66% | **1.7%** |
| 追加試行（参考・盲検でない） | あり | R を見た後に直した対応表 | 2.0%（2/99） | 97% | — |
| **対応表あり盲検** | あり | 正しい対応表だけを渡した（R・既存の議事録は見ていない） | **2.0%**（2/99） | 97% | 0% |

- 対応表あり盲検：`output_MeetingMinutes/20261120_Bさんヒアリング/evidence_log/20261120_Bさんヒアリング_対応表あり盲検/`。採点表は `eval_nishiyama/scores_W.tsv`。
  - 誤りは R068・R103 の2件だけで、どちらも R 側の付与が疑わしい。除けば 0%。
  - 追加試行と件数・誤り箇所まで一致した。盲検でも同じ精度が出ることを確かめた。
  - 作成時間は ④ 4.8分＋⑤ 0.8分。④は文字起こしを読んだ時間を含まない。

- 全体の誤り率は、あり・なしでほぼ同じ（差 0.9ポイント）。ただし誤りの中身が違う。
  - **pyannote ありの誤りは、対応表の1か所（Fさん→Dさん）の取り違えだけ**。これを除くと 1.7%。
  - 対応表を直せば一括で消える。追加試行の 2.0% のうち2件も、R 側の付与が疑わしい箇所（R068・R103）。
- **pyannote なしの誤りは、聞き手の質問全体に散らばる**。
  - Fさん・Aさんの質問の多くを「I【推定】」にまとめた。Fさんの説明の一部はBさんの発言に取り込んだ。
  - Aさんの発言は1件も当てられなかった。
  - 一括では直せず、1件ずつ聞き直す必要がある。Fさんを除いても 10.0%。
- 【推定】の数：なし 31件、あり（基本試行）21件。
- 基本試行は「該当なし」が 28件と多い。これは当時の書き方（要約が強い）によるもので、pyannote の有無とは関係ない。

**CI（指名型・5人、R の記載 25件）**

| 版 | pyannote | 誤り | 【推定】なしで正解 | 【推定】付きで正解 |
|---|---|---|---|---|
| 話者記号なし | なし | **0件** | 24件 | 1件 |
| 基本試行 | あり（Gさん・Eさんが同じ記号） | **0件** | 16件 | 9件 |
| 追加試行（参考・盲検でない） | あり | 0件 | 25件 | 0件 |

- 司会が順に指名するので、pyannote がなくても誤りは 0件。【推定】はむしろ少ない。
- 注意点：
  - スキルの format-spec.md の例文に、この会議の R の文（R001・R016）が使われていた。この2件を除いても結果は同じ（なし：22件が【推定】なしで正解、1件が【推定】付き）。
  - R の件数が少ない（25件）ので参考扱い。

**網羅への影響（上の「もう1つの役割」）**
- CI では、pyannote がないと抜けの補完で戻る文字が 1/10（+388字 → +38字）。
- Cさんでは差は小さい（+239字 → +217字）。

**判定基準に当てはめると（案）**

| 会議の種類 | 話者の付与 | 抜けの補完 | 判定（案） |
|---|---|---|---|
| 指名型（CI） | 差なし（0件 vs 0件） | pyannote で +350字 | 話者の付与には不要。抜けの補完の役割は残る |
| 自由発言のヒアリング（Bさん） | 対応表を正しくすれば、なしより 8〜10ポイント良い（基準の 5ポイント以上） | 未計測 | **必要**。ただし対応表を人が確認することが前提 |
| 2人の対話（Cさん） | 未評価（R なし） | 差は小さい | 正解付けの後に判定 |

- **pyannote の価値は「声で発言を正しく分ける」ことにある**。誰がどの記号かを当てる部分は弱い。
- なしの場合は、Claude が内容から推定する。聞き手どうし（似た立場の人）を区別できない。
- ありの場合でも、AI の推定だけでは、1か所の取り違えで1人分の発言がすべて誤る。人が冒頭を聞いて対応表を直せば、誤りはほぼなくなる（ISSUE-001 の「ヒアリングでは対応表を人が作る」と同じ結論）。

**pyannote を使うべき場面・使わなくてよい場面（定性的な整理）**

考え方：Claude は「誰が話しているか」を内容から推定できる。推定できない場面でだけ、声で区別する pyannote が要る。表の根拠の列で、「実測」は今回の比較で確かめたもの、「見込み」は仕組みから考えたもの（未検証）。

| | 場面 | 理由 | 根拠 |
|---|---|---|---|
| **使うべき** | 自由に発言する会議で、聞き手（質問する側）が複数いる | 立場の似た人どうしは内容で区別できない。なしの版はFさん・Aさんの質問をIさんにまとめた | 実測（Bさん） |
| | 名前で呼ばれない参加者がいる | 呼ばれない人には内容からは発言を当てられない（Aさんは0件） | 実測（Bさん） |
| | 発言者の区別が議事録の価値に直結する（誰の意見か・誰の宿題か・確度の書き分け） | 誤りの害が大きい | 検証計画 3.3 |
| | Whisper が取りこぼしやすい録音（長い沈黙、小さい声、雑音） | 抜けの補完が pyannote の発話区間を使っている | 実測（CI：+388字 → +38字） |
| **使わなくてよい** | 司会が順に指名する会議（チェックイン、報告順の決まった定例） | 指名の直後の発言は誰か分かる | 実測（CI：なしでも誤り0件） |
| | 話者名付きの文字起こしがある（Teams など） | 話者が最初から付いている | ISSUE-002 |
| | 発言者を問わない用途（話題・決定事項だけでよいメモ） | 話者の誤りが問題にならない | 見込み |
| | 2人の対話で、質問する側・説明する側がはっきりしている | 役割で区別できる | 見込み。Cさんで未評価 |
| **使っても効かない** | 2人の声が似ている、片方の発言が少ない | 1つの記号にまとめられる | 実測（Cさん、ISSUE-022） |
| | 対応表を AI の推定だけで作る | 1か所の取り違えで1人分の発言がすべて誤る | 実測（Bさん：Fさん19件） |

運用上の結論（案）：pyannote を使うなら、話者対応表の人の確認とセットにする。人が確認しないなら、自由発言の会議でも pyannote なしと誤り率は変わらない（21.2% vs 20.3%）。

**残る確認**
1. ~~「pyannote＋正しい対応表だけ」の盲検~~ → 2026/11/23 実施。2.0%（R 側が疑わしい2件を除けば 0%）で、追加試行と同じ結果。
2. Cさん（2人の対話）の正解付け（Aさん）。
3. ~~抜けの補完を pyannote なしでも保つ方法~~ → 2026/11/23 Aさん：検討不要。

## 選択肢

| 案 | 内容 | 良い点 | 懸念 |
|---|---|---|---|
| A | 常に pyannote を使う（今のまま） | 判断が要らない | 処理時間の66%を使い続ける。2人の会議ではほぼ役に立たない（ISSUE-022） |
| B | 会議の種類で使い分ける（会議情報ファイルに「話者分離：する/しない」の欄を設ける） | 必要な会議だけ時間をかける。複数会議をまとめて処理する時の効果が大きい | 記録者が会議ごとに選ぶ必要がある。種類の判定基準が要る |
| C | pyannote をやめ、発言者は Claude の内容判断だけにする | 処理時間が約3分の1になる。構成が単純になる | 自由発言の会議で話者誤りが増える可能性がある |
| D | 常に使うが、軽い設定（ずらし幅を広げる）にする（ISSUE-018） | 速さと精度の中間 | 精度の落ち方を測る必要がある（比較中） |

推奨：上の評価を先に行い、その結果で B か D を選ぶ。C はBさんヒアリング（自由発言）での結果を見るまで決めない。

## ソフトへの影響

- B の場合：会議情報ファイル（`src/meeting_info.py`）に「話者分離：する/しない」の欄を追加し、`run_pipeline.py` がそれを見て②を飛ばす。
- C の場合：`.venv-diar`・pyannote・Hugging Face のトークンが不要になり、環境構築が簡単になる。
- 議事録作成スキル：pyannote なしのときの発言者推定の手順（【推定】の付け方）を決める（ISSUE-023 と関連）。
