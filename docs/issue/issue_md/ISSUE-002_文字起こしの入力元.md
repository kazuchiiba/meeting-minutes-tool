## 何が起きているか・何が分からないか

検証計画は「Teams などの文字起こし」を入力に想定しているが、今回は録音（m4a）を Whisper で文字起こししている。作るソフトがどちらを入力にするかで、構成が変わる。

## 根拠

- 検証計画 1章「Teams などの文字起こしテキストを入力にして」
- INPUT にあるのは m4a の録音のみ

## 選択肢

| 案 | 内容 | 良い点 | 懸念 |
|---|---|---|---|
| A | 録音 → Whisper ＋ pyannote | 対面会議・録音だけの会議にも使える | 処理時間がかかる。話者名の対応付けが要る |
| B | Teams の文字起こしファイル（.vtt / .docx） | 話者名付き。処理が軽い | Teams 会議でしか使えない。文字起こしを有効にし忘れると使えない |
| C | 両方を受け付け、共通の形式に変換してから議事録を作る | 用途が広い | 作る量が増える |

## ソフトへの影響

入力部分の設計が変わる。議事録作成部分は「話者付き・タイムスタンプ付きのテキスト」という共通形式にしておけば、どの案でも使い回せる。

## 決定内容

2026/11/23 Aさん：入力は次の3通りすべてに対応する。
1. 音声ファイルのみ（Whisper ＋ pyannote）
2. テキストのみ（Teams・Notion などの文字起こし）
3. テキスト＋音声：Teams・Notion の文字起こしに加えて音声も入力し、両方を突き合わせて議事録の精度を上げる
- 残りの対応：入力形式ごとの読み込みと、テキストと音声の突き合わせ（時刻・話者の照合）の実装。
- 2026/11/23 Aさん：提案のとおり、入力を3通りにする実装をする（発言者はテキスト、本文は Claude が両方を見て判断・判断できなければ【推定】、同じ名前で組み合わせ、参加者はテキストの話者名で自動入力）。
- 対応：`src/import_text.py`（.vtt / .docx / .txt / .md の自動判定、取り込み、時刻による話者の対応付け）を作成し、`src/run_pipeline.py` を3通りの入力に対応。作成ルール14、議事録作成スキル、設計書 5.1 に反映。CI の文字起こしから作った見本（Teams .vtt / .docx、Notion .md）で、テキストのみ・テキスト＋音声の両方が動くことを確認した（テキスト＋音声：388/388 セグメントに話者名を付けた）。
- 残り：実物の Teams・Notion のファイルでの確認（見本と形式が違えば読み込み処理を調整する）。
