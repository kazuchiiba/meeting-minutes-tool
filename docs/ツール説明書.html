1. ツールの目的

会議の録音から、人手で書いた議事録と同じ書式の Word 議事録を、事実に忠実に作ること。

項目 内容
使う人 議事録の記録者。
AI の出力を確認・修正して、最終成果物にする
最優先 正しい事実としての議事録。発言にないことを書かない。拾える発言は漏らさない
（具体例・経緯を本文で省かない）
後回し 処理速度（漏れのない議事録ができてから検討。docs/issue/issue_md/ISSUE-018）
守ること 会議の音声はクラウドサービスに送らない（文字起こし・話者分離はローカルで行う）
出力 人手版と同じ書式の Word（冒頭に会議情報の表、【決定事項】【TODO】【会議内容】）。
確認が必要な箇所は黄色の蛍光ペン

2.2 Python 環境（venv を2つに分ける理由）

faster-whisper と pyannote は依存ライブラリ（numpy、huggingface_hub、torch）のバージョンが衝突するため、venv を分けている。

venv 用途 主なパッケージ 一覧
.venv 文字起こし、抜けの補完、自己点検、Word 出力、Issue 一覧、用語集 faster-whisper 1.2.1、ctranslate2 4.9.1、av 19.0.2、numpy 2.5.5、python-docx 1.2.0、openpyxl 3.1.5、pypdfium2・pillow（PDF 確認用） requirements-whisper.txt
.venv-diar 話者分離 pyannote.audio 3.3.2、torch 2.5.1+cpu、torchaudio 2.5.1+cpu、numpy 1.26.4、huggingface_hub 0.25.2、lightning 2.4.0、av 19.0.2 requirements-diar.txt

バージョン固定が必要な理由（実際に起きた不具合）

  • pyannote.audio 3.3.2 は、torchaudio 2.9 以降で AttributeError: torchaudio.AudioMetaData になる → torch / torchaudio を 2.5.1 に固定。
  • pyannote.audio 3.3.2 は use_auth_token 引数を使うため、huggingface_hub 1.0 以降では動かない → 0.25 系に固定。
  • pyannote の依存（pyannote.core など）は新しいメジャー版と互換性がない → 5.0.0 などに固定。
  • PyAV 19 では faster-whisper 内蔵の音声読み込みが失敗する → 音声は自前の src/audio_io.py で読み込み、配列で渡す。

設定 値 理由

5.3 ② 話者分離 src/diarize.py

$env:PYTHONUTF8=1; .venv-diar\Scripts\python src\diarize.py INPUT\<名前>.m4a --speakers <参加人数>
  • pyannote 3.1（CPU）で話者区間を求め、.diarization.json に保存する。
  • --speakers に参加人数を指定する（指定しないと自動推定）。
  • Whisper の各セグメントに、時間の重なりが最も大きい話者を割り当てる（src/merge_speakers.py）。同じ話者が続く行はまとめて .speakers.txt に出力する。
  • 出力の話者は SPEAKER_00 などの記号。氏名との対応表は人が作る（ヒアリング形式では AI の推定が誤った。docs/issue/issue_md/ISSUE-001）。
  • 既知の限界：声の近い2人を1人と判定することがある（CI でGさん・Eさんが同じ記号になった）。

5.4 ③ 抜けの補完 src/fill_gaps.py

$env:PYTHONUTF8=1; .venv\Scripts\python src\fill_gaps.py INPUT\<名前>.m4a

Whisper が長い発言を数文字に潰す不具合への対策（docs/issue/issue_md/ISSUE-011）。CI では約70秒の報告が「承知です。」の5文字になっていた。

検出の条件 処理
10秒以上のセグメントで、1秒あたり1.5字未満（通常の発話は5〜8字/秒） pyannote が発話を検出した部分だけを VAD なしで文字起こしし直し、置き換える
pyannote が3秒以上の発話を検出しているのに、Whisper のセグメントが20%未満しか覆っていない 同様に文字起こしして追加する

補完した区間は .meta.json の gap_fill に記録し、話者を割り当て直して .speakers.txt を作り直す。

見出しの付け方（人手版の2会議から読み取った規則。会議の種類は Claude が冒頭のやり取りから判断する）

会議の種類 見分け方 見出しの形 区切り方
チェックイン形式（CI など） 司会が「〇〇さんお願いします」と順に指名する 〇〇さんの会議/議題名 指名された人ごとに区切り、その人の報告の中で話題（予定・タスク・相談事項）が変わるところでさらに区切る。質疑はその話題の見出しの下に入れる。全員向けの連絡は 全体/…
ヒアリング形式 聞き手が質問し、相手が業務を説明する 取引先・対象/区分：内容 聞き手の新しい質問、「最後に取引先Q…」などの話題の切り替え、画面共有の開始で区切る。取引先・対象（取引先P、取引先R、取引先Qなど）が変わったら見出しの前半を変える

ヒアリング形式の区分は、その見出しの中のやり取りの性質で決める。

区分 使う場面
確認 業務の内容・流れ・仕組みを質問して確かめるやり取り
課題 話し手が困っていること、手間・不具合が起きていること
懸念 まだ起きていない、または起きているか分からないが、問題になりうること

4.1 正解データの作成

評価者は文字起こしをもとに、次の2つを作る。どちらも両版を見る前に確定させる。

(a) 発言セグメント一覧 発言をひとまとまりごとに区切り、次の項目を付ける。

列 内容
セグメントID 連番
発言者 実際の発言者

(b) キーポイント一覧 議事録に載るべき主張IDの一覧。事実、課題、決定事項、宿題を含める。

4.2 突き合わせ

R と C の各記載項目について、評価者が次の項目を付ける。

  • 記載上の発言者
  • 記載上の確度（語尾で判定する）
  • 根拠になる発言セグメントID（複数可。根拠がなければ空欄）

4.4 合格基準

次の5つをすべて満たせば、C は R と同等以上と判定する。

  1. C の付け足しが 0 件
  2. C の確度の格上げが 0 件
  3. C の無断推定が 0 件
  4. C の話者誤りが R 以下
  5. C の網羅数が R 以上

1〜3 は件数 0 の絶対基準、4〜5 は R との相対基準にしている。議事録で最も害が大きいのは「言っていないことが書かれる」ことなので、そこは相対評価にしない。

評価の扱い（2026/11/23 追記。docs/issue/issue_md/ISSUE-004・ISSUE-010） - 取捨選択：R は記録者が意味があると判断したものだけを書く。AI にはその判断を求めず、拾えるものはすべて拾う。R にない記載は、発言に根拠があれば誤りとしない。網羅は「R に書かれた項目を C がどれだけ含むか」で見る。 - 正確さの基準：書式・取捨選択は R、事実の正確さは発言（文字起こし・音声）を基準とする。R の言い換え・書き直しは、意味が同じなら差分として扱わない。 - 文体：話し言葉の崩れた語順は、意味を変えずに書き言葉に整える（主語を前、述語を後にする等）。

4.5 手順

  1. 音声から文字起こしを作り、手段と設定を記録する。
  2. 評価者が正解データ（4.1）を作って確定させる。
  3. Claude に文字起こしと付与情報を渡し、C を作る。作成時間を記録する。
  4. 評価者が R と C を突き合わせる（4.2）。
  5. 指標を集計し、合格基準で判定する（4.3、4.4）。Lean の verify 関数でも同じ判定を確認する。
  6. 差分一覧（抜け・誤り・付け足し）を作り、不合格項目の原因を分類する（文字起こしの誤り / 作成ルール違反 / 文脈不足）。
  7. 汚染ありの本試行の結果を踏まえ、別の会議で盲検の本番試行を行う。

5. Lean による形式化

MinutesVerification.lean には、4.3 の指標と 4.4 の合格基準をそのまま関数として定義している。Lean 4.15.0 で型検査済み。

定義・定理 内容
evaluate 正解データと議事録から指標を集計する
passes / verify 合格基準による判定。R と C は同じ関数で評価する
fabrication_fails 付け足しが1件でもあれば不合格になる（証明済み）
overclaim_fails 確度の格上げが1件でもあれば不合格になる（証明済み）
coverage_shortfall_fails 網羅数が R を下回れば不合格になる（証明済み）

サンプルデータ 10/30 ヒアリングの一部を使った仮データで、良い例は合格、付け足しのある例は不合格になることを確認

形式化で保証できること 判定基準があいまいにならないこと、R と C に同じ基準が適用されること、基準どうしが矛盾しないこと。

形式化で保証できないこと 正解データ（セグメントの区切り方、確度の付け方、キーポイントの選び方）が正しいかどうか。ここは人の判断で、検証結果の信頼性はその品質で決まる。

6. 限界

  • 確度は「推測 < 伝聞 < 本人認識 < 確認済み」の全順序に単純化している。伝聞と本人認識は本来比較しにくい。
  • キーポイントに重要度の重みを付けていない。重要な発言の抜けも、些細な発言の抜けも同じ1件として数える。
  • 要約の良し悪し（何をまとめ、何を省くか）は網羅数でしか測れない。読みやすさは参考指標にとどめている。
  • 1会議だけの結果なので、傾向は分かっても一般化はできない。複数の会議で繰り返すことが望ましい。

何が起きているか・何が分からないか

人手版（R）には決まった書式があるが、自動版（C）は独自の書式で作ったため、見た目も読み方も大きく異なる。ソフトで再現するには、書式を明文化する必要がある。

根拠

R から読み取れる書式： - 参加者は敬称略、所属付き、記録者に「(記)」：「当社：C、D、G、E、A(記)」 - 【会議内容】の下を「〇〇さんの会議/議題名」で区切る：「Cさんの会議/Praの予算申請」 - 発言は1段落にまとめ、末尾に（発言者・敬称略）：「…学びたいところは学びたい。(C)」 - 発言者の一人称・口調を残す：「Nさんと私に落ちてきた」 - 質問は疑問文で書き、回答と交互に並べる：「Auth認証エラーはPythonでやっているのか。(A)」

  • 話し言葉の崩れた語順は、意味を変えずに書き言葉に整える（主語を前、述語を後にする等）。（2026/11/23 Aさん、ISSUE-010 より）

C は人ごとに「予定・タスク・質疑」で区切り、行頭に「Cさん：」、三人称の伝聞体で書いた。

Bさんヒアリングで分かったこと（2026/11/23 追記）

ヒアリングの R は CI と書式が違う。 - 見出し：「取引先/区分：内容」（例：「取引先P/課題：現場配送品で請求金額が丸め誤差で1円ズレる」）。区分は 確認・課題・懸念・活動・コメント。 - 画面共有された資料の位置に「[マニュアル]」などの画像の差し込み枠を置く（ISSUE-013）。 - 参加者は組織・グループを階層で書く（ISSUE-008）。 - 取引先・社内用語はカタカナ・略称に統一する（取引先P、取引先R、取引先S、当社グループ）。 → 案 B（会議の種類ごとにテンプレート）が必要。
