# 議事録 自動作成 検証計画

- 版数：Ver0.1（2026/11/22）
- 対応ファイル：`MinutesVerification.lean`（判定ロジックの形式化）

---

## 1. 目的

**検証する問い**
会議の音声ファイルだけを入力にして、AI（Whisper ＋ 話者分離 ＋ Claude）が人手の Word 議事録と同等以上の議事録を作れるか。

**作れない場合に明らかにすること**
1. 妥協点：AI に任せられる範囲と、人が補う範囲の境目（例：下書きは AI、確度と話者の確認は人）
2. 解決すべき課題：妥協点で運用するために、解決しなければならない課題と、その原因（文字起こし / 話者分離 / 議事録作成 / 文脈不足）

課題と妥協点の候補は `docs/issue/issue_md/` に起票し、検証の結論として本書の末尾にまとめる。

**判断に使う場面**
今後のヒアリングで、議事録作成に AI を使うかどうかを決める。使う場合は、人がどこを確認すればよいかも決める。

**「同等以上」の定義**
正確性（書いてあることが発言どおりか）と網羅性（重要な発言が拾えているか）の2点で判定する。読みやすさは参考扱いとし、合否には使わない。

| 項目 | 内容 |

| 論点・不明点 | 比較で出た論点は `docs/issue/issue_md/` に起票する |

## 3. 条件

### 3.1 入力条件

| 項目 | 条件 |
|---|---|
| 文字起こし | 修正せずにそのまま渡す（誤変換も含めて試す） |
| 文字起こし手段 | 使った手段と設定（Teams / Stream / Word トランスクリプトなど）を記録する |
| 付与情報（基本試行） | 参加者の氏名・所属のみ |
| 付与情報（追加試行・任意） | 用語集（MDB、HATLi、子会社X、取引先S、検収T など）と会議の目的。結果は基本試行と分けて記録する |

### 3.2 公平性の制約と、分かっているバイアス

| バイアス | 影響 | 対処 |
|---|---|---|
| Claude は人手版 R を既に読んでいる | 内容を知っているので C が有利になる | 本試行は「汚染あり・参考扱い」と明記する。本番の判定は、別の会議で R を見せずに行う（盲検） |
| 正解データの作成者が R か C を先に見る | 作成者の判断が引っ張られる | 正解データは両版を見る前に確定させる。できれば両版の作成者以外が作る |
| 人手版は記録者が会議の文脈を知っている | 取捨選択では R が有利 | 前提として受け入れる。追加試行で目的を渡した場合との差も見る |

### 3.3 自動版の作成ルール（事前に宣言しておく）

1. 発言にないことは書かない。
2. 確度は語尾で書き分け、発言より強く書かない。
   - 確認済み：「〜している」「〜である」
   - 本人認識：「〜と認識」「〜とのこと」
   - 伝聞：「〜と聞いている（〇〇より）」
   - 推測：「〜と推測」「〜の可能性」
3. 誤変換で内容を推定した箇所には【推定】を付ける。聞き取れない箇所は【聞き取り不明】とし、推測で埋めない。
4. 確定に確認が必要な事項には【要確認：確認先】を付ける。
5. 記録者の注記は「※記：」として、発言とは分けて書く。
6. 決定事項・宿題は末尾にまとめて書く。

## 4. 確認方法

### 4.1 正解データの作成

評価者は文字起こしをもとに、次の2つを作る。どちらも両版を見る前に確定させる。

**(a) 発言セグメント一覧**
発言をひとまとまりごとに区切り、次の項目を付ける。

| 列 | 内容 |
|---|---|
| セグメントID | 連番 |
| 発言者 | 実際の発言者 |
| 主張ID | 何についての発言か（同じ内容には同じIDを振る） |
| 確度 | 確認済み / 本人認識 / 伝聞 / 推測 |
| 誤変換フラグ | 文字起こしが崩れていて、内容が推定になる箇所か |

**(b) キーポイント一覧**
議事録に載るべき主張IDの一覧。事実、課題、決定事項、宿題を含める。

### 4.2 突き合わせ

R と C の各記載項目について、評価者が次の項目を付ける。

- 主張ID
- 記載上の発言者
- 記載上の確度（語尾で判定する）
- 根拠になる発言セグメントID（複数可。根拠がなければ空欄）
- 【推定】などの明示があるか

### 4.3 指標

| 指標 | 定義 | Lean での名前 |
|---|---|---|
| 付け足し | 根拠になる発言がない記載 | `isFabricated` |
| 確度の格上げ | 発言より強い確度で書いた記載（例：「多分」を断定に） | `isOverclaim` |
| 話者誤り | 根拠はあるが、発言者を取り違えた記載 | `hasSpeakerError` |
| 無断推定 | 根拠が誤変換箇所だけなのに【推定】の明示がない記載 | `isUnflaggedGarbled` |
| 網羅数 | 根拠つきで記載できたキーポイントの数 | `covers` |
| 確度の格下げ（参考） | 発言より弱い確度で書いた記載 | `isUnderclaim` |
| 読みやすさ（参考） | 5段階の主観評価。関係者2名以上で採点 | — |
| 作成時間（参考） | 議事録の作成と、人による確認にかかった時間 | — |

### 4.4 合格基準

次の5つをすべて満たせば、C は R と同等以上と判定する。

1. C の付け足しが 0 件
2. C の確度の格上げが 0 件
3. C の無断推定が 0 件
4. C の話者誤りが R 以下
5. C の網羅数が R 以上

1〜3 は件数 0 の絶対基準、4〜5 は R との相対基準にしている。議事録で最も害が大きいのは「言っていないことが書かれる」ことなので、そこは相対評価にしない。

**評価の扱い（2026/11/23 追記。docs/issue/issue_md/ISSUE-004・ISSUE-010）**
- 取捨選択：R は記録者が意味があると判断したものだけを書く。AI にはその判断を求めず、拾えるものはすべて拾う。R にない記載は、発言に根拠があれば誤りとしない。網羅は「R に書かれた項目を C がどれだけ含むか」で見る。
- 正確さの基準：書式・取捨選択は R、事実の正確さは発言（文字起こし・音声）を基準とする。R の言い換え・書き直しは、意味が同じなら差分として扱わない。
- 文体：話し言葉の崩れた語順は、意味を変えずに書き言葉に整える（主語を前、述語を後にする等）。

### 4.5 手順

1. 音声から文字起こしを作り、手段と設定を記録する。
2. 評価者が正解データ（4.1）を作って確定させる。
3. Claude に文字起こしと付与情報を渡し、C を作る。作成時間を記録する。
4. 評価者が R と C を突き合わせる（4.2）。
5. 指標を集計し、合格基準で判定する（4.3、4.4）。Lean の `verify` 関数でも同じ判定を確認する。
6. 差分一覧（抜け・誤り・付け足し）を作り、不合格項目の原因を分類する（文字起こしの誤り / 作成ルール違反 / 文脈不足）。
7. 汚染ありの本試行の結果を踏まえ、別の会議で盲検の本番試行を行う。

## 5. Lean による形式化

`MinutesVerification.lean` には、4.3 の指標と 4.4 の合格基準をそのまま関数として定義している。Lean 4.15.0 で型検査済み。

| 定義・定理 | 内容 |
|---|---|
| `evaluate` | 正解データと議事録から指標を集計する |
| `passes` / `verify` | 合格基準による判定。R と C は同じ関数で評価する |
| `fabrication_fails` | 付け足しが1件でもあれば不合格になる（証明済み） |
| `overclaim_fails` | 確度の格上げが1件でもあれば不合格になる（証明済み） |
| `coverage_shortfall_fails` | 網羅数が R を下回れば不合格になる（証明済み） |
| `no_fabrication_of_all_supported` | 全項目に根拠があれば付け足しは 0 件になる（証明済み） |
| `same_certainty_not_overclaim` | 確度を発言どおりに書けば格上げにならない（証明済み） |
| サンプルデータ | 10/30 ヒアリングの一部を使った仮データで、良い例は合格、付け足しのある例は不合格になることを確認 |

**形式化で保証できること**
判定基準があいまいにならないこと、R と C に同じ基準が適用されること、基準どうしが矛盾しないこと。

**形式化で保証できないこと**
正解データ（セグメントの区切り方、確度の付け方、キーポイントの選び方）が正しいかどうか。ここは人の判断で、検証結果の信頼性はその品質で決まる。

## 6. 限界

- 確度は「推測 < 伝聞 < 本人認識 < 確認済み」の全順序に単純化している。伝聞と本人認識は本来比較しにくい。
- キーポイントに重要度の重みを付けていない。重要な発言の抜けも、些細な発言の抜けも同じ1件として数える。
- 要約の良し悪し（何をまとめ、何を省くか）は網羅数でしか測れない。読みやすさは参考指標にとどめている。
- 1会議だけの結果なので、傾向は分かっても一般化はできない。複数の会議で繰り返すことが望ましい。

## 8. 暫定結論（2026/11/23、11/20 の2会議・基本試行）

詳細：`docs/verification/20261120_CI_比較.md`、`docs/verification/20261120_Bさんヒアリング_比較.md`、`docs/issue/issue_md/`

**問い：音声ファイルだけから、AI が Word のような議事録を作れるか**
→ **現時点では作れない。ただし「下書き」としては使える水準にある。**

| 観点 | CI（28分・指名形式） | Bさんヒアリング（63分・自由討議） |
|---|---|---|
| R の主要な話題を C が含むか | 11/11 すべて含む | 主要な話題はすべて含むが、細かい質疑8件が抜けた |
| 付け足し（発言にないこと） | 目視で0件 | 印なしの誤った言い換え3件（ISSUE-014） |
| 話者誤り | 0件（2名の混同を内容から正しく振り分け） | 13発言（FさんをDさんと誤認、ISSUE-001） |
| 社内用語・人名 | 誤変換多数（ISSUE-005・006） | さらに多い |
| 処理時間（CPU のみ） | 約2時間 | 約8時間（ISSUE-012） |

**妥協点の候補**
1. AI：文字起こし、話者分離、議事録の下書き（全発言を拾う）、確認が必要な箇所の一覧化
2. 人：話者と氏名の対応表の作成（ヒアリングでは必須）、【推定】【聞き取り不明】箇所の確認、画面共有資料の貼り付け

**解決すべき課題（優先順）**
1. 無断推定・話者誤りをなくす（議事録の信頼性に直結）：ISSUE-014、ISSUE-001
2. 用語集・人名簿の整備：ISSUE-005、ISSUE-006（`docs/design/議事録作成用の用語集.xlsx`）
3. 抜けをなくす自己点検の段を設ける：ISSUE-015
4. 会議の種類ごとの書式：ISSUE-003、ISSUE-013
5. 処理時間と実行環境：ISSUE-012、ISSUE-002

**次の検証**：用語集を確認したうえで、用語集＋話者対応表を渡す追加試行を行い、上の表がどこまで改善するかを測る。
