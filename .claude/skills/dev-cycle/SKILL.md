# 開発サイクル

```
 ┌→ 1. 要件定義 → 2. 実装 → 3. 評価 → 4. Issue 起票 ─┐
 └──────────────── 次のサイクル ←───────────────────┘
       サイクルを締めるとき：5. 詳細設計書 → 6. ツール説明書（HTML）
```

| 工程 | 出力 | 置き場所 | 使うスキル |
|---|---|---|---|
| 1. 要件定義 | 設計書（md） | `docs/design/議事録作成ツール設計書.md` | — |
| 2. 実装 | コード | `src/`、`.claude/skills/minutes/` | — |
| 3. 評価 | テスト結果（JSON → Excel・md） | `docs/verification/` | `minutes`（議事録を作る）、`verification` |
| 4. Issue 起票 | Issue 一覧（Excel）と Issue 内容（md） | `docs/issue/` | `issue` |
| 5. 詳細設計書 | コードごとの詳細設計書（md） | `docs/design/design_detail/` | `design-detail` |
| 6. ツール説明書 | 人が読む HTML | `docs/ツール説明書.html` | `tool-manual` |

**md は AI が読むもの、HTML は人が読むもの。** 5・6 はサイクルを締めるときに1回だけ行い、1〜4 の途中では行わない（コンテキストと時間の節約）。

## 進め方

### 0. 現在地を確かめる

`docs/design/開発サイクル記録.md` の最後のサイクルを読み、どの工程まで終わったかを確かめて、記録者に伝える。

### 1. 要件定義

- 入力：前のサイクルで「決定」になった Issue、記録者からの新しい要望。
- 設計書を更新し、版数を上げる（例：Ver0.4 → Ver0.5）。変えた章を記録に書く。
- **記録者が決めていないことは要件にしない。** 決めるべきことは Issue にして記録者に聞く。

### 2. 実装

- **実装に入る前に、記録者の承認を取る**（プロジェクトの `CLAUDE.md`「実装の前に必ず確認を取る」）。変えるファイル・挙動・既定値・既存の結果への影響を示し、明示的な了承を得てから始める。
- 設計書の変更に合わせてコード・スキルを直す。
- 動作を確かめる（構文チェック、小さな入力での実行）。
- 変えたファイルを記録に書く。

### 3. 評価

- `minutes` スキルで議事録を作り、`verification` スキルで結果を記録する。
- 処理時間・自己点検の件数・人手版との比較を、前のサイクルと比べる。
- run_id を記録に書く。

### 4. Issue 起票

- 評価で見つかった問題・論点を `issue` スキルで起票する。対応が終わった Issue は「済」にする。
- 記録者に、新しい Issue と、決めてほしいことを伝える。
- ここで記録者の回答を待つ。回答が出そろったら、次のサイクルの 1 に進むか、サイクルを締めるかを記録者に確認する。

### 5〜6. サイクルを締める（記録者が「締める」と言ったとき）

1. `design-detail` スキル：変わったコードの詳細設計書だけを書き直す。
2. `verification` スキルの `build_report.py`、`issue` スキルの `build_issue_list.py` で一覧を作り直す。
3. `tool-manual` スキル：`docs/ツール説明書.html` を作り直す。
4. 記録の「締め」欄に日付を書き、HTML のパスを記録者に伝える。

## 記録の書き方（`docs/design/開発サイクル記録.md`）

サイクルごとに次の表を追記する。工程が終わるたびに該当の行を埋める。

```markdown
## サイクル N（YYYY/MM/DD〜）

| 工程 | 状態 | 出力・内容 |
|---|---|---|
| 1. 要件定義 | 済 / 実施中 / 未着手 | 設計書 VerX.X。変えた章 |
| 2. 実装 | | 変えたファイル |
| 3. 評価 | | run_id |
| 4. Issue 起票 | | 起票した Issue、済にした Issue |
| 5. 詳細設計書 | | 書き直したファイル |
| 6. ツール説明書 | | 作成日時 |
```

## 注意

- Agent（サブエージェント）は使わない。記録者の判断が必要な工程が多く、工程は前の出力に依存するため、1つずつ順に進める。
- 会議の音声をクラウドに送らない（設計書 2.5）。
