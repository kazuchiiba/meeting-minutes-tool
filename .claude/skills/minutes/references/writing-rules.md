# 議事録の書き方（正本）

議事録作成（④）のルール。書式（表・見出しの形・文体）の固定仕様は [format-spec.md](format-spec.md)。根拠は `docs/verification/議事録検証計画.md` 3.3 と `docs/issue/issue_md/` の決定事項。ルールを変えたら、このファイルと設計書 5.5 の要約を両方直す。

## 1. 作成ルール

| No. | ルール | 根拠 |
|---|---|---|
| 1 | 発言にないことは書かない | 検証計画 3.3 |
| 2 | 確度は語尾で書き分け、発言より強く書かない（確認済み「〜している」／本人認識「〜と認識」「〜とのこと」／伝聞「〜と聞いている（〇〇より）」／推測「〜と推測」「〜の可能性」） | 検証計画 3.3 |
| 3 | 文字起こしにない語に直した箇所は `語【推定：「元の語」】`、聞き取れない箇所は `【聞き取り不明：「元の語」】`、確認が必要な箇所は `【要確認：内容】`。**印を付けずに言い換えない**。崩れた箇所も飛ばさずに印を付けて残す。元の語は必ず「」で囲む（⑦の候補抽出で使う） | ISSUE-014・015 |
| 4 | **拾えるものはすべて拾う**。何を省くかは記録者が判断する。会議終了後の会話も残す | ISSUE-004・011 |
| 5 | **質問と回答は対で残す**。質問を回答側の説明に盛り込んでもよいが、情報を落とさない | ISSUE-015 |
| 6 | **本文では具体例・経緯・数字・固有名詞を省かない**。要約してよいのは【決定事項】【TODO】だけ | ISSUE-015 |
| 7 | 話し言葉の崩れた語順は、意味を変えずに書き言葉に整える（主語を前、述語を後）。一人称（私）はそのまま残してよい | ISSUE-003・010 |
| 8 | 用語・人名は用語集の正式表記で書く。用語集の誤変換例に当たる語は、印なしで正式表記に直してよい | ISSUE-005 |
| 9 | 画面共有された資料（「見せながら」「これ」「ここのデータ」など）がある見出しには、`[(画像内容名)]` の枠を置く。枠は**その見出しの会話の最後**に置く（Word 出力でも自動で最後に移る） | ISSUE-013・023 |
| 10 | 冒頭に【決定事項】【TODO】をまとめる。TODO は「内容（担当：氏名、期限：…）」。決まっていなければ「明確な決定事項はなし」と書く | ISSUE-009 |
| 11 | 発言者は文末に `(氏名)`（敬称略）。内容から推定した場合も、**確度が高ければ `(氏名)` と書く**。本当に怪しい場合（どちらの発言か内容から判断できない）だけ `(氏名【推定】)`、分からない人は `(不明)` | ISSUE-001・003・023 |
| 12 | 会話に出てくる人名は用語集の「人名」シート（名簿）で確認する。名簿にない、または表記が確かでない人名は `氏名【要確認：人名】` として残し、記録者が最後に直す | ISSUE-006 |
| 13 | **会話のやり取りを字下げで表す**。やり取りの最初の発言は通常の行、やり取りが一段落するまでの応答・続きは行頭に半角スペース2つを付ける（Word では1段下げた ✧ になる）。新しい話題・新しい説明が始まったら、通常の行に戻す | ISSUE-023 |
| 14 | **テキスト＋音声**では、発言者はテキスト（Teams など）の話者名に従う。本文は Whisper（`.speakers.txt`）とテキスト（`.text.txt`）を突き合わせ、片方にしかない発言は拾い、食い違う箇所は文脈に合う方を採る。どちらとも判断できなければ【推定：「もう一方の表記」】を付ける | ISSUE-002 |

## 2. 見出しの付け方

会議の種類は会議情報ファイルの「会議の種類」に従う。空欄なら冒頭のやり取りから判断し、【AI作成メモ】に判断したことを書く。

| 会議の種類 | 見分け方 | 見出しの形 | 区切り方 |
|---|---|---|---|
| チェックイン形式（CI など） | 司会が「〇〇さんお願いします」と順に指名する | `〇〇さんの会議/議題名` | 指名された人ごとに区切り、その人の報告の中で話題（予定・タスク・相談事項）が変わるところでさらに区切る。質疑はその話題の見出しの下に入れる。全員向けの連絡は `全体/…` |
| ヒアリング形式 | 聞き手が質問し、相手が業務を説明する | `取引先・対象/区分：内容` | 聞き手の新しい質問、「最後に〇〇…」などの話題の切り替え、画面共有の開始で区切る。取引先・対象が変わったら前半を変える |
| どちらでもない | — | 話題ごとに `議題/内容` | 話題が変わるところで区切る。迷ったら記録者に確認する |

ヒアリング形式の区分：

| 区分 | 使う場面 |
|---|---|
| 確認 | 業務の内容・流れ・仕組みを質問して確かめるやり取り |
| 課題 | 話し手が困っていること、手間・不具合が起きていること |
| 懸念 | まだ起きていない、または起きているか分からないが、問題になりうること |
| 活動 | 話し手が行った取り組み（提案など） |
| コメント | 聞き手側の意見・所感・今後の方針 |

見出しの議題名・内容は、その区切りの中の発言から作る。発言にない言葉で見出しを作らない。

## 3. md の書式（`src/make_docx.py` の入力）

```markdown
# 会議名
| 日時 | 2026/11/20(金) 時刻不明（録音 約38分） |
| 場所 | |
| 参加者 | 部署：氏名、氏名(記) / 部署：氏名 |
| 資料 | 画面共有（本文中の [(画像内容名)] の箇所） |

【決定事項】
- 決定事項。(発言者)
【TODO】
- 内容（担当：氏名、期限：…）

【会議内容】
## 取引先P/確認：内容
質問や話題の切り出し。(発言者)
  それへの回答。(発言者)
  続きのやり取り。(発言者)
新しい説明の始まり。(発言者)
  それへの質問・回答。(発言者)
[(画像内容名)]

> 本議事録は、録音から AI（Whisper ＋ pyannote ＋ Claude）が自動作成した（付与情報：参加者氏名＋用語集＋話者対応表）。
> 話者対応表：SPEAKER_00＝〇〇、SPEAKER_01＝〇〇（記録者が確認）
> 黄色の【推定】【聞き取り不明】【要確認】は、確認が必要な箇所。
```

- 参加者の所属は用語集の「人名」シートから取る。記録者には `(記)` を付ける。
- 日時の時刻・場所は音声から分からなければ空欄または「時刻不明」とし、推測で書かない。
- 末尾の `>` の行は、Word の【AI作成メモ】にまとまる。
